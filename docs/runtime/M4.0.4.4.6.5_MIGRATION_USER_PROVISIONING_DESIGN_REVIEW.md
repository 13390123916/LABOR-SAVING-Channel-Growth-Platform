# M4.0.4.4.6.5 Migration User Provisioning Design Review Report

## 1. User Provisioning Requirements

This review defines the minimum specification for a migration runtime user.
It is a design artifact only. It does not authorize or perform `CREATE USER`,
`ALTER USER`, `GRANT`, `REVOKE`, database creation, migration execution, seed,
reset, or service changes.

The provisioning change requires all of the following before execution:

- an Approved Operator and recorded permission-change approval;
- an explicitly approved target `DATABASE_URL` and confirmed target database;
- a secret injected outside Git, reports, scripts, and `.env.example`;
- an approved username, host rows, authentication plugin, and privilege set;
- a pre-change account/privilege snapshot and a verified target backup artifact;
- a written partial-failure and rollback procedure;
- a post-change verification record linked to the operator and target.

The prior recovery chain establishes administrator authentication availability,
but it does not satisfy these execution requirements.

## 2. Migration User Identity Design

### Recommended migration identity

```text
Username: labor_saving
Purpose: Prisma migration execution only
Secret source: Approved external secret injection
```

`labor_saving` is the username already referenced by the repository runtime
configuration. Renaming it would be a separate compatibility and approval
decision. The repository must not receive the password or any credential value.

The application runtime should use a separate least-privileged identity when
it enters runtime provisioning. Reusing a migration identity for application
traffic is not recommended because it would expose DDL-capable privileges to
the application process.

## 3. Host Scope Decision

The active instance reports `skip_name_resolve=1`; host matching is therefore
address-oriented. Host rows must use explicit connection-source addresses,
not DNS names and never `%`.

Recommended decision:

```text
Primary row:  labor_saving@127.0.0.1
Optional row: labor_saving@::1, only if the approved runtime path requires IPv6
Denied:       labor_saving@%, hostname-based rows, broad network ranges
```

The final row set remains BLOCKED until the Approved Operator confirms whether
the runtime uses IPv4 only or both tested TCP paths. The target URL must also
use the approved canonical host so that host matching is deterministic.

## 4. Authentication Plugin Recommendation

Recommend `caching_sha2_password` for a new MySQL 8 account, subject to a
compatibility check against the installed Prisma/MySQL connector and the
approved TLS or secure local connection path. Do not copy the plugin used by
existing root rows merely for convenience.

Fallback to `mysql_native_password` requires an explicit compatibility and
security approval because it is a weaker legacy choice. The selected plugin,
TLS requirement, account lock state, password expiry policy, and secret
rotation owner must be recorded before provisioning.

## 5. Privilege Boundary Design

The migration identity is a controlled DDL identity for the approved target
schema, not a server administrator.

Migration scope may include only the schema-level capabilities required to
apply and inspect the approved Prisma migrations, including creation and
alteration of tables, indexes, constraints, and the Prisma migration history
record. It must not include global administration, account management,
`GRANT OPTION`, replication, shutdown, file access, or access to unrelated
databases.

The application runtime identity must be separate and limited to the CRUD
operations required by the running platform. It must not receive migration
DDL or account-management privileges. Any exception requires a documented
security review and explicit approval.

Privilege verification must compare the exact post-change grants with the
approved manifest; a successful login alone is insufficient evidence.

## 6. Database Scope Design

The intended target is:

```text
Database: labor_saving_channel_growth
Instance: active E:\\MySQL Server 8.0.46 instance
Port:     3306
```

The database is not currently confirmed as present in the active instance.
Provisioning must not create or select a database implicitly. The Approved
Operator must first confirm the database identity, ownership, environment
(Local/Staging/Production), character set/collation policy, and explicit
`DATABASE_URL` before any account grant is considered.

## 7. Security Review

Security controls for this design are:

- no credentials stored in the repository or review report;
- no root substitution for the migration identity;
- no wildcard host scope;
- no `skip-grant-tables`, `init-file`, process termination, or service restart;
- no permission mutation without an Approved Operator and target approval;
- migration and application identities separated;
- account state, grants, and audit evidence verified after change;
- the design does not modify frozen architecture, ADRs, schema, or migration SQL.

Administrator access is an enabling precondition only. It is not provisioning
authorization and it is not migration execution authorization.

## 8. Rollback Strategy

Before provisioning, capture a read-only snapshot of the target account rows,
authentication metadata, grants, target database identity, and operator
approval record. Generate and verify the required target backup artifact before
the migration execution chain proceeds.

If provisioning fails before account creation, stop and preserve the instance.
If a new account was created and the approved rollback is invoked, remove only
that newly created account through a separately authorized change. If an
existing account was altered, restore its recorded prior plugin, lock/expiry
state, and grants through a separately authorized change. Never issue an
automatic rollback or broaden privileges to recover from a partial failure.

Record the failure point, exact target, operator, timestamp, affected account
rows, rollback result, and remaining risk. A rollback of account state does not
replace the required database backup for later migration rollback.
