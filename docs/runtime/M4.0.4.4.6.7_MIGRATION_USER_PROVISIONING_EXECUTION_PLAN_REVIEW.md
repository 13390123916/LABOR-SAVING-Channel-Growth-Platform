## 4. User Creation Procedure

The controlled procedure is intentionally expressed as operator actions rather
than executable SQL:

1. Verify the approval manifest and read-only pre-change account snapshot.
2. Confirm that the approved username is `labor_saving` and that no conflicting
   account row exists for the approved host.
3. Create only the approved account row or rows using the approved plugin and
   externally injected secret.
4. Apply only the approved target-schema privilege manifest.
5. Do not alter root, global accounts, unrelated databases, or server settings.
6. Stop immediately on any error, unexpected row, or privilege mismatch.
7. Record the exact result before running validation.

These actions are not authorized by this document and were not performed.

## 7. Privilege Grant Plan

The migration identity is limited to the approved target schema and the
capabilities required to apply and inspect the approved Prisma migration
history, tables, indexes, and constraints.

The approval manifest must explicitly exclude global administration, account
management, `GRANT OPTION`, replication, shutdown, file access, and unrelated
databases. The application runtime identity must remain separate and must not
receive migration DDL privileges.

The operator validates the final grants against the manifest by exact comparison
and records any unexpected privilege as a failure. The privilege manifest is
currently design-only and not approved.

## 8. Secret Injection Plan

The secret is retrieved from an approved external secret manager immediately
before the controlled change and injected into the operator process through its
approved secret mechanism. It must never be written to repository files,
reports, shell history, logs, CI variables visible to jobs, or `.env.example`.

The plan requires documented secret owner, rotation interval, revocation path,
exposure response, and post-change cleanup. A local development password is
not an acceptable secret source for this plan.

Current status: external secret source and injection evidence are absent.

## 9. Backup Before Change

Before any account or privilege mutation, the operator must create and verify a
backup artifact for the confirmed target database. The evidence must include
target identity, creation timestamp, operator, storage/retention location,
integrity check, and restore owner.

If the target database is absent, the backup gate fails. Account provisioning
must not proceed on the assumption that a future database creation will make
the backup valid.

Current status: verified backup artifact is not available.

## 10. Rollback Procedure

Rollback is a separately approved action, not an automatic recovery step:

- before creation: stop and preserve the instance;
- after a newly created account: remove only that approved new row if rollback
  authority is invoked;
- after an alteration: restore the recorded prior plugin, lock/expiry state,
  and grants;
- after a partial grant: revoke only the unintended approved-scope delta and
  record residual risk;
- for later migration failure: use the verified database backup and the
  migration rollback runbook, not account rollback as a substitute.

Every rollback record must contain failure point, target, operator, timestamp,
affected rows, action, result, and remaining risk. Rollback approval and
evidence are currently absent.

## 11. Validation Procedure

After an approved change, validation must be read-only and performed in this
order:

1. Confirm the account exists only for the approved host rows.
2. Confirm authentication plugin, lock state, expiry state, and connection
   identity through the approved connection path.
3. Confirm the target database identity and successful least-privilege login.
4. Compare exact grants with the approved migration privilege manifest.
5. Confirm no global, unrelated-database, account-management, or
   `GRANT OPTION` privilege is present.
6. Record validation output without storing credentials.
7. Stop before Prisma migration execution; migration execution is a separate
   approval gate.

No validation command was run during this plan review.
