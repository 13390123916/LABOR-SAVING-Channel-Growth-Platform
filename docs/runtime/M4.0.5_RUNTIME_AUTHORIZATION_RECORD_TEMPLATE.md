# M4.0.5 Runtime Authorization Record Template

Use one repository-external JSON record for one live read-only validation or controlled migration operation. Validate it against `M4.0.5_RUNTIME_AUTHORIZATION_RECORD.schema.json` and reference it from one Evidence Package. This template is a field guide, not an authorization instance.

Structural validation does not use an authorization record. Never create a record with invented operator, approver, target, approval, or evidence values. Never place passwords, raw connection strings, private keys, access tokens, or database output in a record.

## Common Record Fields

```text
record_id: <immutable-record-id>
evidence_package_id: <matching-package-id>
operation_id: <approved-change-or-operation-id>
milestone: M4.0.5
execution_scope: <live-readonly-validation | controlled-migration>
approved_commands: <non-empty-array-of-exact-command-names>
runtime_environment: <local | staging | production>
target_id: <approved-target-id>
target_host: <approved-host>
target_port: <integer-port>
target_database: <approved-database>
database_url_source: <local-env | process | secret-store>
database_url_fingerprint: <non-secret-fingerprint>
operator: <named-operator-and-role>
approver: <named-approval-authority-and-role>
approval_reference: <external-approval-reference>
approval_timestamp: <ISO-8601-date-time>
approval_expiry: <ISO-8601-date-time>
maintenance_window: <object-with-starts_at-and-ends_at>
migration_user_provisioning_component_id: <matching-package-component-id>
live_validation_component_id: <matching-package-component-id>
failure_stop_conditions: <non-empty-array-of-stop-conditions>
decision: <scope-valid-decision>
decision_timestamp: <ISO-8601-date-time>
```

For `controlled-migration`, also require:

```text
migration_set: <non-empty-array-of-approved-migration-identifiers>
authorized_release_owner: <named-release-owner-and-role>
backup_component_id: <matching-package-component-id>
rollback_component_id: <matching-package-component-id>
```

## Decision States

- `BLOCKED`: the record may document a reviewed denial, but preflight must reject it.
- `READY_FOR_LIVE_VALIDATION`: only the exact approved live read-only commands may enter preflight.
- `READY_FOR_CONTROLLED_EXECUTION`: only the exact approved controlled commands may enter preflight; no execution is implied.
- `EXECUTED`: historical result state; preflight must reject reuse.

## Contract Rules

- `approval_expiry` is always a real date-time and must be later than `approval_timestamp` and the evaluation time.
- `maintenance_window.starts_at` must be earlier than `maintenance_window.ends_at`; preflight must run inside that window.
- `approved_commands` is an exact allowlist for one operation and cannot mix live and controlled commands.
- Component IDs must match the referenced Evidence Package components.
- Migration-user provisioning remains an independent prerequisite. A general authorization decision cannot override a `BLOCKED` provisioning component.
- Backup, rollback, and live-validation evidence are referenced through the Evidence Package rather than duplicated in this record.
- Raw `DATABASE_URL` values, credentials, secrets, private keys, tokens, backup contents, and live database output are prohibited.
