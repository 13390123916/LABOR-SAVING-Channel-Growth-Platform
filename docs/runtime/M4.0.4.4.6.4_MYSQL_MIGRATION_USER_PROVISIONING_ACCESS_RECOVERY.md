# M4.0.4.4.6.4 MySQL Migration User Provisioning & Access Recovery Report

## 1. Scope and Governance Impact

This stage covers controlled provisioning or restoration of the configured
`labor_saving` migration user for the approved runtime database.

It does not authorize migration execution, seeding, reset, schema changes,
Prisma changes, or frozen architecture changes. `CREATE USER`, `ALTER USER`,
`GRANT`, and `REVOKE` are database state changes and require an explicitly
approved operator, an approved target `DATABASE_URL`, and a recorded rollback
and failure procedure.

## 2. Previous Evidence

The preceding M4.0.4.4.6.3 assessment established:

- an active MySQL administrator credential can authenticate;
- the configured `labor_saving` account was not returned by `mysql.user`;
- host matching is address-oriented because `skip_name_resolve=1`;
- the effective TCP accounts include `root@127.0.0.1` and `root@::1`;
- no account, privilege, password, service, database, or migration change was run.

Administrator authentication is evidence for a possible controlled recovery
session only. It is not approval to substitute root for the configured
migration user or to mutate privileges.

## 5. Controlled Next Action

After explicit approval is supplied, the Approved Operator must:

1. Confirm the active MySQL instance and target database identity.
2. Decide and record the exact `labor_saving` host rows and authentication
   plugin, retaining the existing `skip_name_resolve=1` boundary.
3. Inject the secret outside Git and run the smallest approved account
   provisioning change.
4. Verify `CURRENT_USER()`, account lock and expiry state, and the exact
   migration grants for both approved connection paths.
5. Generate and verify a real pre-migration backup artifact before returning
   to migration execution review.
6. Record operator, timestamp, target, commands, result, and rollback outcome.

Until those inputs exist, the correct action is to preserve the active
instance and remain stopped at the access-recovery boundary.

## 6. Security Controls

- Credentials remain outside repository files, reports, scripts, and Git.
- Root is not treated as a substitute migration identity.
- `skip-grant-tables`, `init-file`, process termination, and service restart
  recovery paths remain prohibited.
- Validation PASS, administrator authentication, and a running MySQL service
  are not migration execution approval.
