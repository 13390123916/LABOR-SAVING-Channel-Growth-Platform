## 6. Security Boundary Review

The following boundaries remain in force:

- no `CREATE USER`, `ALTER USER`, `GRANT`, `REVOKE`, database creation, or
  database deletion;
- no wildcard host, hostname-based row, or privilege outside the approved
  target schema;
- no root substitution for the migration identity;
- no `skip-grant-tables`, `init-file`, service restart, or process termination;
- migration DDL identity remains separate from the application runtime identity;
- no Prisma migration, seed, reset, schema edit, migration SQL edit, ADR edit,
  or frozen architecture change.

The authorization review itself has not crossed the database permission-change
boundary.

## 7. Backup Requirement

provisioning authorization is converted into execution approval for the
migration chain. The artifact must include target identity, creation time,
operator, retention location, integrity verification, and restore owner.

Account provisioning is not a substitute for a database backup. If the target
database is absent, the backup gate cannot pass and no provisioning or
migration authorization may be inferred from the running MySQL service.

## 8. Rollback Requirement

Before authorization, record a read-only snapshot of relevant account rows,
authentication metadata, grants, target identity, and the approved design.
The runbook must define separately authorized actions for:

- stopping before account creation;
- removing only a newly created account;
- restoring prior plugin, lock/expiry state, and grants after an alteration;
- handling a partial failure without broadening privileges;
- rolling back later database migrations using the verified database backup.

The record must name the rollback authority and capture operator, timestamp,
target, failure point, action, result, and residual risk.
