# M4.0.5 Runtime Evidence Package Repository Boundary

## Purpose

This document defines the repository contract for a future live read-only validation or controlled migration Evidence Package. It is repository governance only. It does not authorize database access, migration-user provisioning, migration execution, acceptance, health checks, transaction smoke tests, seed, reset, or privilege changes.

## Boundary

The repository contains only:

- this boundary document;
- the Evidence Package JSON Schema;
- the external Evidence Component Descriptor JSON Schema;
- the Runtime Authorization Record JSON Schema and field template;
- static governance validation and runtime preflight logic.

Real Evidence Package manifests, authorization records, approval tickets, backup metadata, rollback records, live-validation records, database output, and execution results must remain outside the repository. Passwords, raw connection strings, private keys, access tokens, root credentials, backup contents, and secret-store values must never enter Git.

`RUNTIME_EVIDENCE_PACKAGE` must identify an absolute repository-external JSON manifest. The non-secret `database_url_fingerprint` is the SHA-256 produced by `calculateTargetBindingDigest` from the canonical environment, target ID, lower-case host, numeric port, database, and URL-source tuple; it is never a hash of a credential-bearing URL. The manifest may contain only non-secret target identity, decisions, component references, SHA-256 digests, timestamps, and blockers. The authorization component must reference an absolute repository-external JSON record whose digest matches the manifest. Every non-blocked provisioning, backup, rollback, or live-validation component must reference an absolute repository-external JSON descriptor that validates against `M4.0.5_RUNTIME_EVIDENCE_COMPONENT.schema.json` and whose digest matches the manifest.

## Package Identity

One package binds exactly one approved operation to one target:

```text
package_id
package_version: 2
operation_id
milestone
purpose
created_at
target_binding
components
component_set_sha256
package_decision
decision_timestamp
```

M4.0.5.7 uses Evidence Package version `2` and Authorization Record version `2`; M4.0.5.6 created no real version-1 instance. Changing the operation, command scope, environment, target, authorization record, component reference, or component digest requires a new package review. A package must not be reused after expiry, outside its maintenance window, or after it reaches `EXECUTED`.

`component_set_sha256` is the SHA-256 of the UTF-8 JSON generated by `calculateComponentSetDigest` in `runtime-execution-preflight.mjs`. The canonical set uses the fixed order `migration_user_provisioning`, `backup`, `rollback`, `live_validation` and binds each present component name, component ID, descriptor ID, operation ID, target ID, status, absolute reference, SHA-256, recording time, validity time, and blockers. Authorization records repeat this digest and each individual descriptor digest; changing any component invalidates the authorization binding.

## Component References

### Authorization

The authorization component references the external Runtime Authorization Record. It must be `AUTHORIZED`, schema-valid, unexpired, within its maintenance window, bound to the same package, operation, target, record ID, exact command set, and component digest set, and have a matching SHA-256 digest.

A READY authorization must contain an approved `BLOCKED -> READY_FOR_LIVE_VALIDATION` or `BLOCKED -> READY_FOR_CONTROLLED_EXECUTION` transition and a digest-bound reference to the superseded BLOCKED package. Packages and descriptors are append-only: a BLOCKED file is never edited into READY; a new package supersedes it.

### Migration-User Provisioning

Migration-user provisioning is an independent prerequisite component owned by gate `M4.0.4.4.6.10`. It must be `COMPLETED` before live database validation or controlled migration can pass preflight. Administrator access, a general Runtime authorization, or a repository validation PASS cannot override `BLOCKED` provisioning evidence.

The component descriptor requires non-secret contracts for identity, host authorization, authentication plugin compatibility, exact privilege manifest, external secret readiness, named approver, and post-validation reference. Its package ID, operation ID, target binding, component identity, status, chronology, transition, reference, and SHA-256 must all match the package. It must not contain a password or raw connection value.

### Backup

Controlled migration requires a `VERIFIED` backup component reference. Its external evidence must bind the backup to the same target and record the artifact identity, storage reference, retention, size, SHA-256 digest, verification time, and responsible owner. Backup contents remain outside the repository and outside the package manifest.

### Rollback

Controlled migration requires a `VERIFIED` rollback component reference. Its external evidence must identify rollback authority, runbook, partial-failure procedure, restore-validation reference, stop conditions, and owner. A documented plan without authority and restore evidence is not verified rollback evidence.

### Live Validation

Live read-only validation requires a `PASS` entry-condition component. Controlled migration requires a `PASS` live-validation result reference bound to the same target and approved migration-user path. A `BLOCKED`, missing, stale, or target-mismatched component fails closed.

## Decision Gate

For `live-readonly-validation`, preflight requires:

```text
package_decision: READY_FOR_LIVE_VALIDATION
authorization: AUTHORIZED
migration_user_provisioning: COMPLETED
live_validation: PASS
```

For `controlled-migration`, preflight requires:

```text
package_decision: READY_FOR_CONTROLLED_EXECUTION
authorization: AUTHORIZED
migration_user_provisioning: COMPLETED
backup: VERIFIED
rollback: VERIFIED
live_validation: PASS
```

Every non-blocked component records `recorded_at`, `valid_until`, and a `BLOCKED -> current status` transition. Descriptor recording must precede component transition; component transition must precede package creation; authorization decision must precede package creation; and package creation must precede package decision. Any missing component, `BLOCKED` status, stale component, expired approval, invalid transition, superseded-package mismatch, internal or missing reference, digest mismatch, command mismatch, operation mismatch, record mismatch, target mismatch, schema failure, or `EXECUTED` record causes preflight to stop before command dispatch.
