# M4.0.5 Runtime Environment Governance

## Purpose

This document defines the repository-side contract for identifying a runtime environment and binding a controlled operation to an approved database target. It does not grant execution authorization and does not contain credentials.

## Required Environment Identity

Every live validation or controlled execution record must declare:

```text
RUNTIME_ENV: local | staging | production
target_id: stable approved target identifier
target_host: approved host name or address
target_port: approved database port
target_database: approved database name
DATABASE_URL_SOURCE: local-env | process | secret-store
```

`RUNTIME_ENV` is mandatory and may contain only `local`, `staging`, or `production`. `target_id` is mandatory and must identify one approved target. The target binding is the tuple of `target_id`, `target_host`, `target_port`, and `target_database`; changing any member requires a new review.

## DATABASE_URL Source Policy

- `DATABASE_URL` is a secret-bearing connection value and must never be committed to Git or copied into governance evidence.
- Local development may load a repository-external `website/.env` when `RUNTIME_ENV=local`.
- Staging and production must receive `DATABASE_URL` from an approved operator process or external secret store.
- Controlled migration commands require a process-level `DATABASE_URL`; `.env`, `.env.example`, and a local default do not prove authorization.
- Evidence may record only a redacted value, a non-secret fingerprint, or the separated host, port, and database fields.

## Environment Rules

### Local

- Local Docker/MySQL configuration is for development and structural preparation.
- `localhost`, `127.0.0.1`, and local credentials are permitted only when `RUNTIME_ENV=local`.
- Local configuration does not authorize staging or production execution.

### Staging

- Staging requires an approved target binding and a named Approved Operator.
- `DATABASE_URL` must be injected into the operator process or approved secret store.
- Localhost, loopback addresses, and `.env.example` defaults are invalid staging targets.
- Backup, rollback, and live-validation evidence must identify the staging target.

### Production

- Production requires an approved target binding, an Approved Operator, and an Authorized Release Owner.
- `DATABASE_URL` must come from the approved production secret path and be present at process scope.
- Localhost, loopback addresses, repository `.env` files, and example defaults are invalid production targets.
- Backup, rollback authority, validation evidence, and the exact approved command must be recorded before execution.

## Command Boundary

Structural commands such as `prisma:generate`, `db:validate`, and `db:acceptance:preflight` are repository-only checks and must not require a live target.

Live read-only commands such as `db:migrate:status`, `db:health`, and `db:tx-smoke` require an explicit process-level `DATABASE_URL`, target binding, and live-validation approval when the environment is not local.

Controlled execution commands such as `db:migrate` and `db:acceptance` require the complete authorization evidence record. Structural validation PASS is not execution authorization.

Runtime code and local-only health/smoke helpers may load a repository-external `.env` only for local development. They must not be used as an implicit source for staging or production controlled execution.

## Stop Conditions

Stop and keep the decision `BLOCKED` when any of the following is true:

- `RUNTIME_ENV` or `target_id` is missing or invalid.
- The target binding is incomplete or does not match the approved target.
- A non-local environment resolves to localhost or a loopback address.
- The controlled process has no explicit `DATABASE_URL`.
- Authorization, backup, rollback, or validation evidence is missing.
- An evidence file contains a raw credential or secret.
